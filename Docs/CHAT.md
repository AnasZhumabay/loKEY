# Защищённый чат — как устроен и что нужно от бэкенда

Контракт версии **1.3.0** (только добавления; чат появился в 1.2.0, в 1.3.0 добавлены группы). Руководство для бэкендера: `Docs/BACKEND_INTEGRATION.md`. Клиентский код: `Core/Chat/`, интерфейс для UI: `Domain/Chat.swift`, экраны: `Features/Chat/`.

## Что видит сервер
Только конверты: `sender_id`, `recipient_id`, `sent_at`, размер и случайные байты `ciphertext`. Текст, имена файлов, вложения и таймеры исчезновения лежат ВНУТРИ шифртекста.
Метаданные (кто с кем и когда) сервер видит всегда — это ограничение любого чата без анонимизации.

## Эндпоинты (все с авторизацией, ошибки — `APIError`)
| Метод | HTTP |
|---|---|
| `registerIdentity(publicKey)` | `PUT /v1/chat/identity` `{public_key}` → `ChatUserDTO` (идемпотентно) |
| `findUser(id)` | `GET /v1/chat/users/{id}` → `ChatUserDTO` (`404` если нет) |
| `send(envelope)` | `POST /v1/chat/messages` → `204` (повтор с тем же `id` игнорировать) |
| `fetch(limit)` | `GET /v1/chat/messages?limit=` → `[ChatEnvelopeDTO]`, старые первыми, не удалять до ack |
| `acknowledge(ids)` | `POST /v1/chat/messages/ack` `{ids}` → удалить из очереди |

Рекомендации серверу: хранить конверты не дольше 30 дней (`expiresAt`), рассылать push **без текста** («Новое сообщение»), ограничить размер конверта (~7 МБ при вложении 5 МБ), rate-limit на `send`, разрешать `send` только если получатель существует.

## Как шифруется (клиент)
1. У каждого пользователя есть пара **X25519**; публичная часть публикуется через `registerIdentity`, приватная лежит в Keychain (`WhenUnlockedThisDeviceOnly`).
2. Контакт добавляется **только очно**: приглашение `lokey://add?id=&u=&k=` (QR) содержит id, имя и публичный ключ. Перед добавлением ключ из QR сверяется с серверным (`findUser`): расхождение = отказ.
3. Из `DH(my, their)` по HKDF-SHA256 получаются две цепочки (по одной на направление).
4. Каждое сообщение: `mk = HMAC(ck, 0x01)`, `ck' = HMAC(ck, 0x02)`; шифрование **AES-256-GCM**, AAD = `отправитель | получатель | счётчик`. Использованный ключ стирается → **forward secrecy** по цепочке.
5. Допускается до 200 пропущенных сообщений; повторы и подмена отклоняются; состояние не меняется после неудачной проверки.
6. Код безопасности (60 цифр) = хэш обоих публичных ключей, одинаков у обоих.

## Исчезающие сообщения, «не пересылать», сверка по QR, CryptoEngine (клиентские, бэкенд не нужен)
- **Исчезающие:** таймер чата и отдельного сообщения (`ChatPayload.ttl`, пресеты 30 с / 5 мин / 1 ч / 1 день / 1 неделя; верхняя граница, принимаемая получателем, — 31 день). Смена таймера чата — служебное сообщение `k="ttl"` (`ttl=0` выкл.). У получателя отсчёт стартует при первом показе. Всё внутри шифртекста; сервер может лишь применять свой максимум очереди (30 дней). Это вежливая функция: скриншот/модифицированный клиент её обходят.
- **Отправка файла из кейса** с флагом «не пересылать» (`nf` в `ChatPayload`): приёмник скрывает «Переслать»/«Сохранить в галерею» и показывает замок. Не защита.
- **Сверка по QR:** `lokey://verify?a=<мой id>&b=<id собеседника>&h=<SHA-256 цифр кода безопасности>` (`ChatVerifyCodec`); сами цифры в QR не раскрываются; результат match / mismatch / wrongContact.
- **CryptoEngine** (`Core/Seams/CryptoEngine.swift`): `ChatRepositoryImpl` работает через протокол; встроенный `BuiltinCryptoEngine` оборачивает `ChatCrypto`. Для libsignal/MLS: написать свой движок, подставить в сборке, поднять `ChatEnvelopeDTO.version`. Нужны prekeys — изменение контракта (подробно `BACKEND_INTEGRATION.md`, 3.6).
- Конверт: клиент ставит `expires_at = sent_at + 30 дней`; повторная отправка после сбоя идёт с тем же `id` (идемпотентно).

## Правка, удаление, реакции, ответы, тема, стикеры
Всё это передаётся **внутри шифртекста** (поля `ChatPayload`: `k` — тип `edit`/`del`/`react`/`theme`, `r` — id сообщения, `rp`/`rt` — ответ, `e` — эмодзи, `s` — стикер, `th` — тема). Для бэкенда это обычные конверты: контракт не менялся.
- **Правка** — только свои текстовые сообщения, в течение 15 минут; у собеседника отображается «изменено».
- **Удаление**: «у меня» (локально) или «у всех» (приходит служебный конверт, у собеседника остаётся пометка «Сообщение удалено»). Получатель удаляет только то, что отправлено этим же отправителем.
- **Реакции**: одна на сторону, двойное касание — ❤️.
- **Тема чата** синхронизируется с собеседником; **стикеры** — крупные эмодзи на цветной подложке (локальный набор из 12), эмодзи-панель с 6 категориями.
- **Сведения о сообщении**: время, статус («принято сервером»), номер одноразового ключа в цепочке, размер шифртекста. Подтверждений прочтения нет.

## Честные ограничения
- Нет DH-храповика (как в Signal Double Ratchet): при утечке долговременного приватного ключа прошлые сообщения защищены, но будущие скомпрометированы, пока ключ не заменят. Для боевого релиза рекомендуется заменить `ChatCrypto` на libsignal/MLS или провести аудит.
- Скриншоты ОС заблокировать нельзя; защита от записи экрана уже есть в приложении.
- История сохраняется между запусками в живом режиме: `HistoryStore` (`Core/Seams/HistoryStore.swift`), AES-GCM ключом аккаунта, файлы исключены из бэкапа; в мок-режиме — в памяти. Состояние сессий (ключи цепочек) — в Keychain.
- Неизвестный отправитель (который отсканировал ваш QR) появляется как непроверенный контакт; в интерфейсе над перепиской висит предупреждение до сверки кода безопасности.
- Группы: контракт и шов готовы (`ChatGroupAPI`, `ChatGroupRepository`), но UI нет, встроенный движок групп не поддерживает (`supportsGroups == false`). Звонки, подтверждения прочтения — не реализованы.
